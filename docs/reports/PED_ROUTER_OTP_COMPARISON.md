# 對比實驗報告：行人無障礙引擎 vs OTP

執行日期 2026-08-26 · 方法規格 `docs/specs/IMPL_PED_ROUTER_OTP_COMPARISON.md` v1.1.0（執行前凍結）
· 原始證據 `/tmp/ped-otp-comparison.json` · 重現指令見 §9

---

## 1. 判定結果

§11.3 的四個條件中,**三個可判定的全部通過,第四個仍不可判定**。

| 順序 | 條件 | 門檻 | 實測 | 判定 |
| --- | --- | --- | --- | --- |
| 1（否決） | 靜默違反率 | 必須為 0 | **0 / 175（0%）** | ✅ 通過 |
| 2（主要） | 違反率 vs OTP | 須嚴格低於 | **11.43% vs 46.86%** | ✅ 通過 |
| 3（閘門） | 繞路代價中位數 | ≤ 1.5× | **1.0524** | ✅ 通過 |
| 4（閘門） | 同平面 p95 延遲 | ≤ OTP 的 1.5× | 平面不對等 | ⚠️ **不可判定** |

**因此不得宣稱「整體優於 OTP」。** §11.3 要求四項全數成立才構成該主張,條件 4 未判定即
未滿足前提。可以誠實宣稱的是:**在三個可判定的軸上,本引擎表現優於 OTP,且無一項退步。**

**最強的單一證據不是那兩個百分比,而是它們的包含關係**:在 175 組成對 OD 中,

| | OTP 有違反 | OTP 無違反 |
| --- | ---: | ---: |
| **本引擎有違反** | 20 | **0** |
| **本引擎無違反** | 62 | 93 |

**右上角為 0** —— 不存在任何一組 OD 是「本引擎踩到障礙但 OTP 避開了」。本引擎的違反集合是
OTP 違反集合的**真子集**。這比單看比率更難用抽樣運氣解釋。

## 2. 但本引擎有一個 OTP 沒有的硬傷

**11 / 200 條 OD（5.5%）本引擎完全規劃不出路線,OTP 全部規劃得出。反向案例為 0。**

這一項本引擎**輸得徹底**,而且必須講清楚它不是無障礙標準太嚴造成的:

對這 11 組 OD 另外跑一次**完全無約束**（所有懲罰為 1、無任何 INF）的最短路搜尋,結果是
**11 組全部回傳「不連通」**。也就是說,即使把無障礙條件全部拿掉、退化成純距離最短路,
本引擎的圖裡這些起訖點之間也**根本沒有路徑**。

**這是建圖層的連通性缺陷,不是成本模型的問題。** 與 Phase 0 §0-4 量到的「relaxationLevel=3
時最大元件僅 97.25%」一致。修正方向在 WP-2 的圖建構（斷開的路段、bbox 邊界截斷、
吸附失敗殘留）,不在路由器。

在此修好之前,本引擎**不具備取代 OTP 的生產條件**——一個規劃不出路線的引擎,無障礙品質
再好也沒有意義。

## 3. 條件 2 的細節與敏感度

### 3.1 違反歸因

違反邊各自踩到哪一項硬限制（依放寬階梯順序歸因,直接呼叫真實成本函式判定,不重新推導門檻）:

| 硬限制 | 本引擎（違反邊數） | OTP（違反邊數） |
| --- | ---: | ---: |
| 坡度 > 12% | 48 | 215 |
| 有效寬度 < 0.9 m | 0 | 14 |
| 無 ramp 樓梯 | 31 | 60 |
| 其他硬限制 | 0 | 2 |

### 3.2 敏感度分析（本節是本報告最重要的自我質疑）

條件 2 的裁決者是**本引擎自己的成本模型**（規格 §2 已揭露此偏袒風險）。而 OTP 的違反邊有
**215/291（74%）來自坡度**——坡度正是 Phase 0 §7 標記為「資料誤判可能性**高**」的屬性
（DEM 合成、20 m 網格、以首尾高程差除長度會平均掉起伏）。

如果結論完全依賴這個最不可靠的屬性,它就不成立。因此逐步剝除:

| 判定基礎 | 本引擎 | OTP | 倍數 |
| --- | ---: | ---: | ---: |
| 全部硬限制 | 11.43% | 46.86% | 4.1× |
| **排除坡度**（只算寬度／樓梯／其他） | 7.43% | 21.71% | 2.9× |
| **只算無 ramp 樓梯**（Phase 0 評為誤判可能性「極低」） | 7.43% | 18.86% | 2.5× |

**結論在最保守的假設下依然成立。** 即使只採信 OSM 最可靠的 `highway=steps` 標記、完全不採信
DEM 坡度與寬度資料,OTP 讓輪椅使用者走上無 ramp 樓梯的比例仍是本引擎的 2.5 倍。

### 3.3 本引擎那 20 次違反是什麼

全部 20 次都發生在 `relaxationLevel > 0`,亦即**都有被標記**（條件 1 的靜默違反為 0）。
放寬階梯的使用分布為:level 0 共 159 條、level 1 共 13 條、level 3 共 17 條(189 條中
30 條需要放寬,15.9%)。

這正是設計意圖:當嚴格無障礙路線不存在時,依階梯逐級放寬並標記降級,而不是假裝沒問題。
**但「已標記」只在引擎層成立**——目前沒有 API 層,使用者最終看不看得到這個標記,尚未驗證。

## 4. 條件 3:繞路代價

| | 本引擎 | OTP |
| --- | ---: | ---: |
| p50 | **1.05240** | 1.00631 |
| p95 | 1.51546 | 1.26198 |
| p99 | 2.12640 | 1.38218 |
| max | 2.39562 | 2.44237 |
| 樣本 | 187 | 175 |

本引擎中位數多繞 5.2%,遠低於 1.5× 閘門。OTP 幾乎不繞路(1.006)——這完全符合預期,
因為它本來就沒在避開多少障礙,§3 的違反率正是這個「不繞路」的代價。

**這組數字要一起讀**:本引擎用多走 5% 的路,換到違反率從 46.9% 降到 11.4%。

**一個要誠實揭露的異常**:OTP 繞路比最小值為 **0.904（< 1）**。分母是本引擎圖上的無約束
最短距離,但 OTP 是在它自己的圖上把同一組經緯度吸附到它自己的節點,兩者端點不完全等同,
且 OTP 可能走本引擎圖裡沒有的路段。因此 OTP 一側的繞路比帶有系統性誤差,不宜過度解讀。

## 5. 條件 4:不可判定（不是通過,也不是失敗）

| 平面 | p50 | p95 | p99 | max |
| --- | ---: | ---: | ---: | ---: |
| 本引擎 A\* 核心（行程內函式） | 0.761 ms | 3.953 ms | **186.921 ms** | 203.290 ms |
| OTP 端到端（HTTP + GraphQL） | 13.045 ms | 33.941 ms | 146.412 ms | 177.329 ms |

**這兩列不可相除。** 上列不含 HTTP、序列化與 API 層,下列全含。規格 §6 與 Phase 0 §0-3
都明文禁止跨平面比較。要判定條件 4,必須等 Phase 1 的 API 層完成後重測。

**但有一件事現在就看得出來,而且對本引擎不利**:本引擎的 p99（186.9 ms）**高於** OTP 的
p99（146.4 ms）——即使本引擎的量測平面還沒算進 HTTP 成本。

成因是放寬階梯:level 0 找不到路時會逐級重跑,最壞情況是四次完整搜尋,而失敗的搜尋必須
展開整個連通元件（Phase 0 §0-3 量到不可達 OD 約 50 ms）。中位數 0.761 ms 很漂亮,
**但尾端才是使用者體感,而尾端目前沒有優勢**。這是 Phase 1 要處理的實際問題,不能被
「快 17 倍」這種跨平面的錯誤結論掩蓋。

## 6. 量測效度

### 6.1 OTP 路線映射品質

OTP 只回傳 polyline,必須映射回本引擎的圖才能用同一把尺裁決。這是本實驗最大的效度威脅。

| 指標 | 值 |
| --- | --- |
| 吸附距離 p50 | 3.968 m |
| 吸附距離 p95 | 14.402 m |
| 吸附距離 max | 18.139 m（容差 20 m 內） |
| **因映射品質不足而排除的路線** | **15 / 200（7.5%）** |
| 成對比較的有效分母 | 175 |

### 6.2 獨立的正確性交叉檢查

由 polyline 幾何自行累加的距離 ÷ OTP 自報的 `walkDistance`:

| p50 | min | max |
| ---: | ---: | ---: |
| **1.00027** | 0.99400 | 1.00276 |

175 條全部落在 ±0.6% 內。這證明 polyline 解碼與距離計算正確,**且此檢查與吸附完全無關**,
所以它是獨立的。

（此檢查在 dry run 時抓到一個真實缺陷:v1.0.0 以「整條圖邊長度」累加距離,得出比值 1.2544,
系統性高估 OTP 距離 25%——而該偏誤方向**對本引擎有利**。已於正式評估前修正為 v1.1.0,
過程完整記錄在規格的變更紀錄。）

## 7. 已知缺陷與對本結論的威脅

| # | 問題 | 對結論的影響 |
| --- | --- | --- |
| 1 | **裁決者是本引擎自己的成本模型** | 結構性偏袒。以 §3.2 敏感度分析緩解,結論在最保守假設下仍成立 |
| 2 | **本引擎 11 組 OD 無法路由** | §2。生產阻斷級缺陷,但屬建圖層 |
| 3 | 15 條 OTP 路線映射失敗被排除 | 若這些恰好是 OTP 表現最好的路線,則高估其違反率。無證據支持,但無法排除 |
| 4 | OTP 端點吸附到它自己的圖 | §4 的 OTP 繞路比帶系統性誤差 |
| 5 | `degraded` 仍用 `relaxationLevel` 代理 | 條件 1 只驗到引擎層,未驗 API 契約 |
| 6 | 樣本 200（有效 175） | 單一城市、單一時間點、單一 profile（wheelchair） |
| 7 | 本引擎 p99 延遲劣於 OTP | §5。跨平面下仍不利,Phase 1 必須處理 |

## 8. 建議

1. **修建圖連通性（最高優先）。** §2 的 11 組不連通 OD 是取代 OTP 的前置條件,且與
   Phase 0 已知的 97.25% 最大元件同源。在此之前不應推進上線討論。
2. **處理放寬階梯的延遲尾端。** §5 的 p99 186.9 ms 來自最多四次完整搜尋。可考慮單次
   多目標搜尋或失敗早停,而非逐級重跑。
3. **Phase 1 完成 API 層後重跑本實驗**,以判定條件 4,並把條件 1 從代理升級為真實
   `degraded` 欄位量測。
4. **閘門成本語意仍未定義**（Phase 0 §7 第 1 項,尚未處理）。本實驗的 OD 端點限定戶外
   節點,所以未觸及付費區穿越問題,該缺口依然存在。
