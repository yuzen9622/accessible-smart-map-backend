# 人行道寬度、入口連通與坡道證據核實

查證日期：2026-10-04。此次重新下載官方資料，讀取隔離候選圖，以來源對照與通道拓樸驗證取代單純 HTTP／建置成功判斷。**結論：取得更明確的來源矛盾與可用證據，尚不能解除正式切換 HOLD。** 正式路網、正式服務與通行規則均未修改。

## 1. 寬度：已確認不可把 Wheelroute width 當淨寬

重新下載[官方人行道 API](https://wheelroute.gov.taipei/wheelrouteApi/api/facility/Get/11)，其 SHA 與先前快照相同。將 15,291 筆與官方 202606 人行道面做 IoU ≥ 0.95 的最佳面配對：14,232 組中，13,840 組（97.25%）`width` 等於 `SW_WTH` 總寬，僅 4,732 組（33.25%）等於 `SWW_WTH` 淨寬；**9,125 組等於總寬但不等於淨寬**。

例如和平東路一段的一筆：Wheelroute width 4.8、官方總寬 4.8、淨寬 2.25。這是欄位內容的交叉證據，不是現地測量。正式[資料平台](https://data.taipei/dataset/detail?id=2b58f15a-dec6-4b9d-91be-4eaccfda5ae7)仍標公分；官網含 m 字串的程式均在註解內，不能據此宣稱主管機關已確認公尺。

**處理決策：保留原始 width、單位 unresolved，不能當作輪椅最小淨寬；也不能把人行道類別的數值推論套用到入口類別。** 詳見[寬度專項報告](a11y-width-verification-2026-10-04.md)及[數值證據](a11y-width-comparison-2026-10-04.json)。

## 2. 入口：取得官方身分與無障礙標示，並找出圖資料矛盾

本次新增讀取兩份捷運公司 CSV：

- [車站出入口座標](https://data.taipei/dataset/detail?id=cfa4778c-62c1-497b-b704-756231de348b)：平台更新時間 2026-08-04；實下載 390 筆，含「是否為無障礙用」。[原始 CSV](https://data.taipei/api/frontstage/tpeod/dataset/resource.download?rid=307a7f61-e302-4108-a817-877ccbfca7c1)。
- [出入口電梯／無障礙坡道 GPS](https://data.taipei/dataset/detail?id=0a3bb422-9eb5-459b-a9d4-138456516183)：平台更新時間 2026-09-02；實下載 193 筆。[原始 CSV](https://data.taipei/api/frontstage/tpeod/dataset/resource.download?rid=61792c82-6609-41b2-9775-3a346934826d)。

兩者使用 CP950；下載成功不表示個別電梯目前正常。沒有向任何機關寄信或提交查詢。

### 身分核對

從現有 GTFS `stops.txt` 取車站／出口名稱，僅正規化臺／台、空白、尾端站字與出口前綴。要求同站同出口唯一對應，且相距 ≤15 m；**不使用最近點猜身分**。

375 個候選入口中有 272 個符合身分與距離條件，其中官方標「是」121 個、「否」151 個。另有 103 個未達此嚴格配對條件，保留未知；可能包括不同營運機關、命名差異或座標偏移，不能自動套用 TRTC 標記。

若只查官方出入口最近位置，375 個中有 348 個在 50 m 內，27 個沒有。前輪使用 Wheelroute 設施點時是 151 個沒有 50 m 內參考點；**新來源補強了位置證據，不能把兩個數字解讀成 124 個入口現地驗收通過**。最近入口不一定是同名入口，更不一定是電梯實際出入口。

臺北車站可直接由官方 CSV 與[站別網頁](https://web.metro.taipei/pages2026/WebStation/051)核對無障礙出口為 M2、M4；本輪不把桃園機捷「臺北車站出口1～7」錯配成 TRTC M1～M8。此例說明為何單靠站名或最近距離不足以建立設備身分。

### 通道拓樸核對

對 272 個身分已對應入口，在同 station_id 的圖內沿有向邊搜尋月台；允許 walkway、moving walkway、elevator、fare/exit gate，排除 stairs、escalator。分別測入口→月台和月台→入口。這是「排除階梯及電扶梯後的圖連通性」，不是完整輪椅成本搜尋，也未檢查設備現況、路面坡度、閘門寬度或所有月台可達性。

找到 **39 筆需複核差異**：

| 官方入口標記 | 圖內結果 | 筆數 |
| --- | --- | ---: |
| 是 | 進、出站都找不到上述路徑 | 24 |
| 是 | 可進、不可出 | 3 |
| 否 | 進、出站均有上述路徑 | 11 |
| 否 | 可進、不可出 | 1 |

這些是資料層矛盾／差異，不是 39 個現場缺失已全部確診。可用的公開點位與目前 GTFS 通道未必為同時期資料；本輪沒有新增或推測通道以消除差異。

具體交叉案例：

- **江子翠出口1**：CSV 標「否」，同名點距離 1.745 m。[捷運公司站頁](https://web.metro.taipei/pages2026/WebStation/084/1)列出口1為樓梯／電扶梯，無障礙出口為3。候選圖卻存在 `出口1 → 手扶電梯六(僅上)1F → 閘門二(內) → 手扶電梯二(站內)B1 → 第一月台` 的全 WALKWAY 路徑。來源 pathway IDs `8827, 2116, 8876, 2133`，現有 GTFS ZIP 中全部 `pathway_mode=1, is_bidirectional=1`，與候選邊一致。**已核實資料契約與官方入口設施描述不一致；不能據此判定這條路可供輪椅通行。** 名稱不是設備 ID，不能僅憑名稱將每一條邊改成電扶梯。
- **忠孝敦化出口2**：官方 CSV「是」，距離 1.824 m；[官方站頁](https://web.metro.taipei/pages2026/WebStation/091/1)也列出口2有電梯、為無障礙出口。候選圖在上述限制下雙向皆無月台路徑，屬需修復／補齊來源對應的漏路候選，不能推論現場沒有無障礙路線。
- **圓山出口1／2**：[官方站頁](https://web.metro.taipei/pages2026/WebStation/056/1)均列為無障礙出口；圖資料只能找到進站、找不到出站的上述路徑。應複核 gate 與 pathway 方向及缺漏，不能直接把所有單向邊改雙向。

## 3. 坡道：核實切分路段，避免把 5,058 條全部判錯

原始 5,058 是有向 crossing 邊，其兩端坡道集合的聯集僅含同一 objectid。此次先用所有 crossing 邊建立無向連通元件；兩端度數1、其餘度數≤2才稱簡單鏈，再檢查整鏈最外側端點的坡道身分。

| 5,058 條有向邊的所屬結構 | 邊數 | 可下的結論 |
| --- | ---: | --- |
| 簡單鏈，整鏈外端配到不同坡道點 | 2,654 | 多數疑點可由 OSM 切分解釋，不能只看單段就判錯 |
| 簡單鏈，整鏈外端坡道證據不足 | 1,178 | 保留未知，不能宣稱無坡道 |
| 分岔或迴圈 | 976 | 無法以單純兩端法解讀，需更細的行穿線／路口拓樸 |
| 簡單鏈，整鏈外端仍僅同一坡道點 | 250 | 仍不能證明整條穿越路段兩端各有坡道 |

例如 `osm:way/131473141` 的一段 7.38 m 邊共享 objectid 2503，但其6節點整鏈的外端有不同坡道點。相對地 `osm:way/378671020` 的例子，即使看3節點整鏈，外端仍只有同一點。

以上不同坡道 objectid 仍可能是重複設施或不同朝向，**不是道路側別／可通行已驗證**。現行 `import-taipei-ramps.ts` 以8 m半徑做多對多 node 配對；`cost.ts` 僅看兩端 HAS_KERB_RAMP boolean 就取消 crossing 加權，沒有驗證兩個獨立坡道或路口拓樸。已確認這個判定的證據強度不足，但不能改成「沒資料就封路」，也不能一律懲罰所有切分子段。正式修正應以完整穿越鏈／側別證據建模並回歸輪椅可達性。
