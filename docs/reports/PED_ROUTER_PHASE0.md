## 0-2 CSR 與記憶體

| 指標                      |                              實測 |
| ------------------------- | --------------------------------: |
| TypedArray 精確 footprint | **18.604 MB**（19,507,204 bytes） |
| 每條有向邊                |                  **43.049 bytes** |
| 六都常駐外推（×4.1）      |                         76.274 MB |
| 六都熱重載峰值（×2）      |                    **152.549 MB** |

### 量測方法：為何不能用 `heapUsed`

同一次載入的兩個記憶體讀數：

| 讀數                                               |            值 |
| -------------------------------------------------- | ------------: |
| `process.memoryUsage().heapUsed` 差值（已強制 GC） |  **0.548 MB** |
| `process.memoryUsage().arrayBuffers` 差值          | **18.661 MB** |
| TypedArray `byteLength` 加總（精確值）             | **18.604 MB** |

`heapUsed` 低估約 **34 倍**。原因是 TypedArray 的 backing store 是 off-heap `ArrayBuffer`，不計入 V8 heap。上位規格 §5.8 已依此更正量測方法；本報告採 `byteLength` 加總作為主數字，`arrayBuffers` 作為獨立交叉驗證（兩者相差 0.057 MB，為載入期間其他暫時性 buffer）。

**連帶的操作面更正**：`--max-old-space-size` **管不到這部分記憶體**。真正的上限是 `docker-compose.yml` 對 backend 設定的 container memory limit，那才是必須設定的那一項。

### 與 §5.8 預算的比對

§5.8 v0.4.0 原訂「CSR 目標：十餘 MB（六都）」。**該目標已被實測推翻**：原估計假設六都約 100 萬條有向邊、每邊十餘 bytes；實際台北一市即有 453,144 條有向邊，依 §3.2 的 4.1 倍外推六都約 186 萬條，且每條實測 43.049 bytes。

**判定：通過。** 但通過的理由是「152.549 MB 這個絕對值對 Node 後端可接受」，**不是**「符合原訂的十餘 MB 目標」。§5.8 已於 v0.5.0 依本次實測更正。

| 統計量 |     值（m） |

**§9.1b 假設「台北捷運車站尺度約在 100–300 公尺量級，此項扣減不會使啟發函數退化到失去引導力」—— 實測支持該假設。** p95 為 138.834 m、最大值 239.300 m，全部落在 300 m 以內。這回答了上位規格 §15 待決項 8。

`min = 0.000` 來自只有單一出入口的群組（該出入口即質心，半徑為 0），屬正常。

### 分組語意的誠實揭露

654 個出入口中，**219 個的 `parentStation` 指向 `locationType=1`（車站）、435 個指向 `locationType=0`（普通站點）**。台北範圍的 120 個群組中，**26 組的 parent 是車站、94 組是普通站點**。

因此 `station_radius_m` 的語意是「同一 `parentStation` 群組內出入口相對質心的最大距離」，**不是**嚴格意義的「車站半徑」。這是 feed 自身的建模方式，不是本次實作的簡化——435 個出入口根本沒有 `locationType=1` 祖先可解析。

## 0-4 吸附品質與延遲

### 吸附失敗率

| 指標   |         值 |
| ------ | ---------: |
| 容差   |       50 m |
| 樣本數 |        200 |
| 失敗   |      **1** |
| 失敗率 | **0.500%** |

樣本取自真實邊幾何上的內插點（`ST_LineInterpolatePoint(ped_edge.geom, fraction)`），即「保證位於某條路上的座標」。

**唯一失敗案例的根因是已知的設計取捨，不是 bug。** 失敗發生在一條 **248.31 m、9 個幾何點的彎曲邊**上。WP-3 的空間索引依上位規格 §4.4 只以「兩端節點連成的線段」近似每條邊（`PedGraph` 契約不攜帶 polyline，以省下 44 萬條折線的記憶體）。對一條長且彎的邊，其幾何中段可以距離端點連線超過 50 m。

這是**可預期且有界的**：只影響長而彎曲的少數邊。若 Phase 1 認為 0.5% 不可接受，解法是在索引中攜帶折線幾何（記憶體代價可估），而非調高容差。

### A\* 核心平面延遲

**量測平面**：`aStar(graph, from, to, wheelchairProfile)` 本身的 wall-clock，**不含**圖載入、不含空間索引建置、不含任何 DB 往返。
**協定**：N = 130 次，**捨棄前 10 次暖機**，保留 120 次（§7.3 協定二要求 N ≥ 100）。
OD 取樣：固定 seed 的實體節點對，取自最大有限互達元件。

| 指標            |       p50 |       p95 |   p99 |   min |    max |
| --------------- | --------: | --------: | ----: | ----: | -----: |
| **延遲（ms）**  | **1.055** | **4.278** | 6.900 | 0.203 | 12.644 |
| `expandedNodes` |     1,463 |     5,078 | 8,245 |    25 | 21,981 |
| `reopenedNodes` |         0 |        31 |    36 |     0 |    119 |

`reopenedNodes` 在 p50 為 0、p95 為 31，證明 §9.1b 的代理座標設計**有效**：接縫處的一致性缺口存在（故有重開）但極小（中位數為零）。重開機制本身是保證最佳性的安全網，其被觸發的頻率低正是該設計成功的證據。

### 不可達 OD 的延遲（分開回報）

| 指標           |        p50 |        p95 |    p99 |    min |    max |
| -------------- | ---------: | ---------: | -----: | -----: | -----: |
| **延遲（ms）** | **50.308** | **65.456** | 68.539 | 48.369 | 72.997 |

不可達 OD 必須把整個連通元件展開完才能確定無解，因此比可達 OD 慢約 **48 倍**。這兩個分布**不可混在一起報**——混合後的 p95 會同時失真於兩種工作量。

**這對 §8.3 的兩趟制有直接的操作意涵**：第一趟失敗時必然支付約 50 ms，第二趟才開始。兩趟制的最壞情況延遲應以「不可達延遲 + 可達延遲」估計，而非可達延遲的兩倍。

### 量測平面對齊的紀律（§7.3 協定一）

**本節數字不得與 §3.6 的 OTP GraphQL 端到端 18–20 ms 直接比較。** 兩者不是同一個量測平面：本節只量 A\* 核心，OTP 的數字含 HTTP、GraphQL 解析、圖查詢與序列化。跨平面比較會得出無意義的結論。成對的同平面比較屬 Phase 6。

## 0-5 §11.3 判定門檻的可量測性

四項條件**皆 `measurable = true`，且皆已量到實際值**（不是只宣稱可量測）：

| #   | §11.3 條件                     | `measurable` | 實測值               |
| --- | ------------------------------ | :----------: | -------------------- |
| 1   | 靜默違反率（否決條件，須為 0） |      ✅      | **0 / 115 = 0.000%** |
| 2   | 標記後違反率                   |      ✅      | 31 / 115 = 26.957%   |
| 3   | 繞路代價（須 ≤ 1.5×）          |      ✅      | 中位數 **1.05699**   |
| 4   | 延遲（同平面 p95）             |      ✅      | p95 **4.278 ms**     |

評估基礎：120 組 OD，其中 115 組回傳路線、5 組無解；逐邊檢查 8,326 條邊。

### 條件 1／2 使用的是代理，必須明說

Phase 0 **沒有 API 層**，因此沒有回應契約中的 `degraded` 欄位可檢查。本次以 **`relaxationLevel > 0` 時回傳路線上實際違反的硬限制** 作為代理指標，欄位名已明確標示（`...UsingRelaxationLevelDegradedProxy`）。

代理的意義：條件 1 量到 0%，代表**引擎不會在未提升 relaxationLevel 的情況下回傳違反硬限制的路線**——這正是「靜默違反」要防的事。但真正的 §11.3 條件 1 要驗的是 API 回應是否帶 `degraded` 標記，那需要 Phase 1 的回應契約才能量。

### 條件 3 的繞路分布與方法

| 統計量                   |          值 |
| ------------------------ | ----------: |
| p50                      | **1.05699** |
| p95                      |     1.38893 |
| p99                      |     2.27985 |
| max                      |    10.21644 |
| 可比較 OD 數             |         100 |
| **排除：含室內邊的路線** |      **15** |
| 排除：零距離             |           0 |

分子為 wheelchair 路線的實際地面距離，分母為「所有懲罰為 1、無 INF」的純距離最短路的地面距離。

**含室內邊的 15 條路線被刻意排除，這是必要的。** 室內邊有成本但**沒有幾何**（`geom IS NULL`），因此它們對「地面距離」的貢獻為零。若不排除，一條大量走室內的路線會算出小於 1 的繞路比（見 §6 的 `indoor_route`，其比值為 0.551），使指標失去意義。任何未來使用此指標的程式都必須沿用相同排除規則。

中位數 1.05699 遠低於 §11.3 閘門 3 的 1.5× 上限。但 p99 為 2.28、max 為 10.22，**尾端存在超過閘門的個案**——§11.3 的判定用的是中位數，故形式上通過，但這條尾巴值得在 Phase 6 檢視。

### 條件 2 與條件 4 在 Phase 0 無法完成判定

§11.3 的條件 2 要求「本引擎須嚴格低於 **OTP 同組 OD** 的違反率」，條件 4 要求「須 ≤ **OTP 同平面** p95 的 1.5×」。兩者都需要 OTP 的成對量測，屬 Phase 6。

> **後續進展（2026-08-26）**：條件 2 已於獨立的成對實驗中完成判定——本引擎 11.43% vs OTP 46.86%，通過，且違反集合為 OTP 的真子集。條件 4 仍因平面不對等而不可判定。同一實驗另發現本引擎有 11/200 組 OD 完全無法路由（图層連通性缺陷）。見 `PED_ROUTER_OTP_COMPARISON.md`。

**Phase 0 只證明了這四項可以自動量測，並非證明它們已通過。** 這正是 0-5 的驗收目標（§7.2：「四項條件是否皆可自動量測」）。

## 6. 人工目視檢查的三條實際路線（§7.4）

**目視判定：這正是 §9 想要的行為，同時也放大了發現 1。** 路線由地面進入車站、**使用兩段電梯**、穿越站內、由另一側出站。這就是上位規格 §9.4 期待的「穿越地下街避開樓梯」「使用電梯」成為引擎可自行推導的路線，而非特例邏輯——已實際發生。

### 目視檢查得到的三個發現

**發現 1：引擎會把捷運付費區當行人捷徑。**
`route_2` 穿過 2 道 `INDOOR_FARE_GATE`，`indoor_route` 走「1 道 fare gate 進、1 道 exit gate 出」。成本模型目前對閘門**不施加任何懲罰**——這是依上位規格 §7.4「未知走中性基準」的正確推論（§7.3 的 profile 表根本沒有閘門這一列，GTFS 也不區分無障礙閘門），但現實後果是引擎把付費區當免費通道。

這**不是實作 bug，是規格缺口**：§7.3 需要為 `pathwayMode` 6/7 定義成本語意。屬 Phase 1 議題，已列入 §7。

**發現 2：含室內邊的路線不可用地面距離計算繞路比。**
`indoor_route` 的地面距離 131.5 m 小於直線距離 238.7 m，算出繞路比 0.551。原因是室內邊有成本但無幾何，地面距離系統性低估。bench 的 0-5 繞路指標已正確排除這類路線（排除 15 條），**任何未來使用該指標的程式都必須沿用相同排除規則**，否則 §11.3 閘門 3 會被室內路線稀釋。

**發現 3：三條路線的吸附距離皆為 0 m。** 因為 OD 是直接取自圖上的實體節點。這使路線檢查聚焦於選路本身，但**沒有覆蓋「任意座標吸附後再規劃」的完整鏈路**。吸附品質由 0-4 的獨立 200 點抽驗負責（失敗率 0.5%）。

### 關於第 7 項

`ped_graph_version.notes` 的 `undirected_segment_count` 與 `edge_type_distribution` 是 WP-2 建圖時寫入的，WP-5 注入室內子圖後只更新了 `node_count` 與 `directed_edge_count`（那兩個是 loader 預先配置 TypedArray 所必需，不一致會直接 throw），沒有回頭更新這兩個統計欄位。

**本報告的對應數字一律取自實際載入的圖，不取自 `notes`**，故不受影響。但若有人日後直接讀 `notes` 做分析，會拿到只含戶外的分布。

**修復（2026-08-26）：** `inject-ped-indoor-graph.py` 現在會一併重算這兩個欄位，並額外寫入拆分欄位
`outdoor_/indoor_/connector_undirected_segment_count` 與 `outdoor_edge_type_distribution`。
無向段數依「一條來源連結算一段」定義：雙向邊成對折半、單向邊各算一段——套用到實際圖為
220,728（戶外）+ 4,989（注入的 pathway）+ 1,125（375 個出入口 × 3）= **226,842**，與本報告 §0-1 實測的無向段數一致。
戶外值以 `outdoor_*` 快照保存，故重複注入不會累加。

**尚未套用到資料庫**：修的是產生 `notes` 的腳本，DB 中 `version_id=1` 的既有 `notes` 仍是舊值，
要等下次執行注入腳本（§8 的重現指令）才會被覆寫。

## 9. 建議

**進入 Phase 1。** Phase 0 的六個驗收項全部有實測數字，且無一構成 go／no-go 的否決。

進入 Phase 1 前應先處理的兩件事：

1. **為 `pathwayMode` 6/7（付費／出口閘門）定義成本語意**（§6 發現 1）。這是規格缺口而非實作缺陷，需要產品決策：是禁止穿越付費區、給予高懲罰、還是回傳時標記「此路線穿越付費區」。在此之前，任何對外展示的路線都可能包含現實中不可行的捷徑。
