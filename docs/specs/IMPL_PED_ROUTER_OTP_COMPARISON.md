# 實作規格：行人無障礙引擎 vs OTP 對比實驗

版本 v1.1.0 · 狀態：**預先登記（pre-registered），正式評估執行前凍結**

本檔在**看到任何結果之前**固定量測程序。判定門檻本身不在此定義——它們已由
`FUNCTIONAL_SPEC_PEDESTRIAN_A11Y_ROUTER.md` §11.3 凍結，本檔不得修改門檻，只補完
「如何取得餵給那些門檻的數字」。

正式評估執行後若發現程序有缺陷，**修正的方式是重跑並在報告中揭露兩次執行**，不是改寫本檔。

### 變更紀錄

**v1.0.0 → v1.1.0（2026-08-26，正式評估執行前）**

以 5 筆樣本做儀器 dry run 時，交叉檢查欄位 `mapped_vs_reported_distance_ratio` 出現 **1.2544**
——映射出的距離比 OTP 自報的 `walkDistance` 長 25%。根因是 §5.2 原本以「被吸附到的整條圖邊長度」
累加距離，但一個 polyline 子段通常只是一條圖邊的一小截，於是同一條邊被反覆計入。

這個缺陷**偏向對本引擎有利**（灌水 OTP 的繞路比，並增加它被判違反的機會），因此在正式評估前修正：

1. **距離改由 polyline 自身幾何計算**（相鄰頂點的 haversine 累加），完全不經過圖邊長度。
2. **受判邊集合改為全域去重**，避免折返路線把同一條邊的違反重複計入。

修正後同一組 dry run 的交叉檢查為 **1.0003**（誤差 0.03%），確認幾何解碼正確。

**完整揭露**：此次 dry run 已看到條件 2 的數字（本引擎 0/5、OTP 2/5）。方法修正是針對上述
可獨立驗證的距離失真，不是為了改變該結果——事實上修正只影響繞路比與違反邊計數，5 筆的
條件 2 結果在修正前後**同為 0/5 對 2/5**，未因修改而改變。dry run 樣本不計入正式評估。

## 1. 這個實驗要回答什麼

§11.3 的四個判定條件中，Phase 0 只完成了條件 1（代理量測）與條件 3。條件 2 與條件 4
需要 OTP 的成對量測。本實驗處理條件 2；條件 4 依 §6 的理由**宣告為不可判定**。

| 條件 | 內容 | 本實驗 |
| --- | --- | --- |
| 1（否決） | 靜默違反率必須為 0 | 量測（仍用 `relaxationLevel` 代理，見 §5.3） |
| 2（主要） | 本引擎違反率須**嚴格低於** OTP 同組 OD | **本實驗的主目標** |
| 3（閘門） | 繞路代價中位數 ≤ 1.5× | 沿用 Phase 0 方法重測 |
| 4（閘門） | 同平面 p95 延遲 ≤ OTP 的 1.5× | **宣告不可判定**（§6） |

## 2. 對比的核心原則：一把尺量兩條路線

兩個引擎對「什麼叫無障礙」的定義不同（OTP 用 OSM `wheelchair` tag 加伺服器端 8.3%
坡度上限；本引擎用 §7.3 的逐邊成本模型）。若各自用各自的標準自評，結果無法比較。

**因此：兩條路線都由「本引擎的成本模型」裁決。** 具體為
`edgeCost(graph, attrIdx, wheelchairProfile(0))` 為 `INFEASIBLE` 即該邊違反硬限制。

這個選擇對本引擎**表面上有利**，必須誠實揭露：我們是在用自己的標準評判對手。但替代方案
更糟——用 OTP 的標準評判會讓「本引擎繞開了 OTP 看不見的障礙」這件事完全不可見。緩解方式是
§5.4 的違反歸因拆解：報告必須說明 OTP 路線的違反**具體踩到什麼**（坡度／寬度／樓梯），
讓讀者能自行判斷該項是否為真實障礙，而非只看一個總違反率。

## 3. OD 樣本（兩引擎完全相同）

| 項目 | 值 |
| --- | --- |
| 樣本數 | 200 |
| 種子 | 20260826 |
| 距離帶 | 直線 300–3,000 m |
| 端點來源 | 圖中**戶外**節點（`source_ref` 非 `gtfs_pathways:*`） |
| 座標傳遞 | 節點的 `lat/lon`，兩引擎收到完全相同的浮點值 |

**端點限定戶外節點的理由**：室內節點是捷運站內的 GTFS pathway 節點，OTP 的圖裡根本沒有
對應物，拿它當起訖點是要求 OTP 回答它無法表達的問題。這不是偏袒任何一方，是排除一個
定義上不對等的比較。

**不得**從「本引擎可路由的最大連通元件」取樣——那會把本引擎路由失敗的案例先行排除，
是明顯的選擇偏誤。取樣自全體戶外節點，路由失敗如實計入 §5.1 的覆蓋率表。

## 4. OTP 查詢參數

| 參數 | 值 | 理由 |
| --- | --- | --- |
| `transportModes` | `[{ mode: WALK }]` | 純步行 |
| `wheelchair` | `true` | 要求 OTP 拿出它最好的無障礙結果 |
| `walkSpeed` | 0.8 m/s | 對齊 `WHEELCHAIR_WALK_SPEED_MPS` |
| `numItineraries` | 1 | 取 OTP 的首選路線 |
| `date` / `time` | 固定值 | 步行不受班表影響，固定以確保可重現 |

取 `itineraries[0]` 的所有 WALK leg,依序串接其 `legGeometry.points`。

## 5. 量測定義

### 5.1 覆蓋率（先於任何違反率）

先報 2×2：兩者都有路線 / 只有本引擎 / 只有 OTP / 兩者皆無。

**違反率一律只在「兩者都有路線」的交集上計算**,確保成對比較。交集外的案例不得
併入違反率的分母或分子,但必須在報告中列出數量——「因為找不到路所以沒有違反」不是優點。

### 5.2 OTP 路線映射到本引擎的圖

OTP 回傳 polyline,不回傳邊 ID,必須映射:

1. 解碼 polyline 為座標序列(精度 5)。
2. 對每一組相鄰頂點,取中點,以 `snapToGraph(index, lat, lon, 20)` 吸附。
3. `edgeAttrIdx` **全域去重**,得到 OTP 路線在本引擎圖上的邊集合。

### 5.2a 距離與判定分離(v1.1.0)

**距離不得由圖邊長度累加求得。** OTP 的地面距離一律取 polyline 相鄰頂點的 haversine 累加,
與吸附結果無關;吸附結果**只用於違反判定**。理由見變更紀錄:子段通常只是圖邊的一小截,
以整條邊長累加會系統性高估 OTP 的距離。

此分離同時提供一個獨立的效度檢查:幾何距離 / OTP 自報 `walkDistance` 應趨近 1.0。
報告必須揭露此比值的分布——它偏離 1.0 即代表 polyline 處理有誤。

**品質守門(這是本實驗最大的效度威脅)**:

- 吸附距離 > 20 m 的子段記為**未映射**。
- 一條路線的未映射子段若超過**10%**,該路線**排除**於違反率計算之外,並計數。
- 報告必須揭露:排除數、吸附距離分布、未映射子段比例。

未做這道守門的話,映射失敗會靜默地變成「OTP 沒有違反」,直接把結論推向錯誤方向。

### 5.3 違反率

| 名稱 | 定義 |
| --- | --- |
| 違反 | 路線含至少一條在 `wheelchairProfile(0)` 下為 `INFEASIBLE` 的邊 |
| 靜默違反(本引擎) | 有違反且 `relaxationLevel === 0` |
| 標記違反(本引擎) | 有違反且 `relaxationLevel > 0` |
| 違反(OTP) | 有違反(OTP 無等價的降級標記機制) |

**代理的誠實聲明**:本引擎仍無 API 層,故沿用 Phase 0 的 `relaxationLevel > 0` 作為
`degraded` 的代理。這量到的是引擎層行為,不是 API 契約。

### 5.4 違反歸因(§2 要求的可稽核性)

對每條有違反的路線,拆出違反邊各自觸發哪一項硬限制:坡度 > 12%、有效寬度 < 0.9 m、
無 ramp 樓梯。兩引擎都要報。這是讓讀者能反駁本報告結論的資訊。

### 5.5 繞路比

沿用 Phase 0 §0-5 方法,含**排除含室內邊路線**的規則(室內邊 `geom IS NULL`,
不排除會算出 < 1 的無意義比值)。兩引擎都以「無約束最短距離」為分母。

## 6. 條件 4(延遲):宣告不可判定

§11.3 條件 4 要求「**同平面** p95」。目前:

- OTP:HTTP + GraphQL 解析 + 圖查詢 + 序列化的端到端。
- 本引擎:行程內函式呼叫的 A\* 核心平面,無 API 層。

兩者不同平面。Phase 0 報告 §0-3 已明文禁止跨平面比較。本實驗**照樣量測兩個數字並列出**,
但標註為「**不可比較,不構成條件 4 的判定**」。要判定條件 4,必須等 Phase 1 的 API 層。

把 1 ms 的核心延遲拿去和 18 ms 的端到端相除得到「快 18 倍」是無意義的,報告不得如此陳述。

---

## 7. 判定輸出

腳本輸出 JSON,報告依 §11.3 的字典序判定:

1. 條件 1 非 0 → 整體失敗,不論其他軸。
2. 條件 2 未嚴格低於 OTP → 不得宣稱「優於」。相同則為「不劣」。
3. 條件 3 > 1.5× → 失敗。
4. 條件 4 → 不可判定,不得用其他軸的優勢抵銷。

**平手處理**:條件 2 相同而 3、4 較佳,只能稱「不劣且更有效率」。
