## 1. 系統概述

本規格書描述在現有無障礙導航後端中新增一個**行人專用的無障礙路徑規劃引擎**（下稱「本引擎」）。

現行引擎分工為 OTP2 負責大眾運輸、Valhalla 負責汽機車、步行同樣委由 OTP2。本引擎接管 `travelMode: "walk"` 的純步行規劃，使「無障礙」從**選路之後的排序條件**變成**選路當下的成本函數**。

本引擎**不是**獨立服務。依 §5 的架構決議，它是後端 Node 進程內的一個模組，另新增一個 PostGIS 容器作為圖資倉儲。OTP2 與 Valhalla 皆不移除。

### 1.1 核心論點

本專案的價值主張不是「自建引擎比較有技術深度」，而是一個可驗證的**能力邊界**問題：

> 個人化無障礙路由需要 per-profile 的成本函數。OTP 2.9 的 per-request 無障礙控制面**只有一個布林值**（`WheelchairPreferencesInput { enabled: Boolean }`），且 schema 註明 wheelchair 是唯一的 accessibility mode；`maxSlope`、`inaccessibleCost`、`slopeExceededReluctance`、`accessEgress.maxDuration` 全屬 `router-config.json` 全域設定，無法 per-request 調整。因此「wheelchair / elderly / visual 各有一組成本函數、跑在同一張圖上」這件事，在 OTP 架構下**不是調參問題，是結構上做不到**。
>
> （來源：`docs/specs/A11Y_SCORING_REWORK.md` §2.5，2026-06-16 查 OTP 2.9 `schema.graphqls` 定論。）

`src/modules/accessible-route/scoring.ts:305` 定義的四個 `MODE_PROFILES`（wheelchair / elderly / visual_impaired / normal）目前完全依賴 post 層排序支撐，而 post 層只能排序 OTP 以同一組全域參數產出的候選。

### 1.2 第二個論點：差異化資料塞不進 OTP

本系統的差異化資料來源**並非 OSM 資料**：

- **hazard 使用者即時回報**（`hazardreports`）——秒級變動
- **TDX 電梯即時故障狀態**——分鐘級變動

OTP 的圖資來源是 OSM PBF，重建一次約 50 分鐘（`src/scripts/build-otp-graph.sh`）。這兩類資料在結構上不可能進入 OTP 的選路決策，只能留在 post 層做事後排序或標記。本引擎的記憶體圖可在單次查詢上疊加動態成本覆蓋（§8.2），使其真正參與選路。

## 2. 問題陳述：現況為何不夠

### 2.1 現行步行規劃流程（as-is）

```
POST /a11y/accessible-route  {travelMode:"walk"}
  │
  ├─ resolveA11yConstraints(mode, {avoidStairs})          service.ts:1600
  │    mode 預設 "normal" → wheelchair 布林 = false
  │
  ├─ planOtpWalkSegments()                                service.ts:2114
  │    [origin, ...waypoints, dest] 拆成相鄰配對，逐段獨立查 OTP 後串接
  │    └─ planOtpWalkDetailed()                           otp-routing.ts:497
  │         wheelchair = avoidStairs ?? (mode === "wheelchair")
  │         walkSpeed  = walkSpeedMps(mode)
  │         └─ queryOtpWalk() → OTP GraphQL                otp-routing.ts:381
  │              送進引擎的無障礙資訊僅有：wheelchair 布林、walkSpeed
  │         └─ selectWalkCandidates()                      otp-routing.ts:473
  │              rankByStairs → 取零階梯前 3 條
  │              全含階梯 → 取階梯最少者 + degraded + 警告
  │
  └─ finalizeDrivingRoutes()                              service.ts:1881
       dedupe → 依 totalMinutes 排序 → hazard 排序 → 取前 3
```

### 2.2 四項已證實的結構性缺陷

**D-1：步行路線完全不經過 `scoreAndRank`。**
`finalizeDrivingRoutes`（`service.ts:1887`）以 `totalMinutes` 排序。`scoring.ts` 的 65/35 加權、`MODE_PROFILES`、tier 權重在 walk 路徑上一次都未被呼叫。因此 walk route 沒有 `scoreComponents` / `accessibilitySummary` 欄位。

**D-2：無障礙判斷退化為「數階梯」。**
實際的無障礙決策只有 `selectWalkCandidates` 的 `rankByStairs`——從 OTP 已給定的候選中挑階梯少者。坡度、路面、寬度、路緣石完全未參與選擇。

**D-3：`avoidStairs` 後處理防線是死碼。**
`walkLegHasStairsBarrier()`（`service.ts:348`）讀取 WALK leg 的 `a11yFacilities`，實測該欄位恆為 `[]`（記錄於 `A11Y_SCORING_REWORK` 與 walk-mode 實測）。

**D-4：同一使用者需求存在兩種互相矛盾的失敗政策。**

| OTP 的回應                       | 現行行為                                                          | 位置                 |
| -------------------------------- | ----------------------------------------------------------------- | -------------------- |
| 回了行程但全部含階梯             | 回**階梯最少那條** + `degraded` + `STAIRS_CONSTRAINT_UNSATISFIED` | `otp-routing.ts:473` |
| `wheelchair=true` 查不到任何行程 | 放寬為 `false` 再探一次；探得到就回 **404 `NO_ACCESSIBLE_ROUTE`** | `service.ts:1609`    |

兩種情境對使用者而言是同一件事（「我要無階梯路線」），卻因 OTP 內部是「回爛路線」或「回空陣列」而得到相反結果。

**D-5（延伸）：多中途點為逐段貪婪。**
`planOtpWalkSegments` 對每個相鄰配對各取 `routes[0]` 後串接，不保證整條路線最佳。

### 2.3 既有的補救已達上限

`deny-foot-on-expressways.py`（PBF 前處理補 `foot=no`、對無 ramp 的 `highway=steps` 注入 `wheelchair=no`）與 `inject-osm-dem-slopes.py`（DEM 合成坡度）已將可在圖資層做的事做完。實測結論：**OTP 將 `wheelchair=no` 視為成本而非硬性禁止**——14 組樓梯 OD 端到端測試中，開啟 `avoidStairs=true` 後僅 2 組真正排除、6 組仍回傳含樓梯路線，且全程無警示欄位。此為引擎內部策略，不在可控範圍內。

**對本專案的三項直接影響**：

1. 成本函數實際可用的輸入為：**距離、樓梯、過街／號誌、surface（27%）、DEM 合成坡度、以及本系統自有的非 OSM 資料集**。
2. 研究貢獻的定位隨之改變——不是「用 OSM tag 計算 cost」（無 tag 可用），而是**「在圖資稀疏的城市，以多來源融合與可信度標記，建構可用且可稽核的無障礙成本模型」**。⚠️ v0.1.0／v0.2.0 在此處把「DEM 合成」列為主要手段，**該定位已修正**——DEM 能補的與無障礙需要的不是同一個尺度，見 §3.6b；真正可能補上缺口的是 §3.7 的政府人行道圖資，但尚未驗證。
3. 資料越稀疏，少數已知事實（5,233 條樓梯、DEM 坡度、使用者回報）越必須是**絕對禁止**而非軟成本，否則會被距離項稀釋。此即 §7.2 硬限制設計的依據。

### 3.4 GTFS 室內圖的幾何限制

`gtfspathways` 端點共 7,037 個 stop，其中 6,998 個存在於 `gtfsstops`。座標狀況：

| `locationType`           | 數量      | 有真實座標 |
| ------------------------ | --------- | ---------- |
| 2 = 出入口               | 654       | **654 ✅** |
| 0 = 月台                 | 467       | 467 ✅     |
| 1 = 車站                 | 1         | 1 ✅       |
| **3 = 通用節點（站內）** | **5,876** | **0 ❌**   |

**已確認為上游來源限制，非匯入缺陷**：原始 `data/gtfs/stops.txt` 中 5,876 列 `location_type=3` 的 `stop_lat` / `stop_lon` **皆為空字串**；`import-gtfs-stops.ts:52-56` 以 `parseFloat("") → NaN` 判定後寫入哨兵值 `0`。GTFS 規格對 `location_type=3` 本即允許省略座標（pathways 以 `traversalTime` 計價，不需幾何）。

此限制直接決定 §9 的室內圖設計：站內以時間計價、無座標節點的啟發函數設為 0。

> 附記（低優先）：此 5,876 筆以 `coordinates: [0,0]` 進入 `2dsphere` 索引。目前不影響任何查詢（自台灣起算的 `$near` 永遠不會取到），但未來若出現無 `maxDistance` 的全域空間查詢需注意。

### 3.5 校園無障礙資料的現況

`campusa11ies` 共 82 校、5,801 筆設施（`facTypeId` 2=無障礙坡道、5=無障礙樓梯等），但：

- **每一筆設施的 `location.coordinates` 皆為空陣列**，僅 82 個學校點有座標。
- 實查 `detailFetchedAt` 為 **0 筆**、`specs` 非空為 **0 筆**。

根因：`campus-a11y-parse.ts:215` 的 `parseCampusFacilityDetail()` 自**單一設施詳情頁**（`POST /Facility/FacilityResult`）的 `data-facility-geo` 取座標，列表頁不帶座標。對應腳本 `pnpm import:campus-facility-detail` **從未執行過**。程式正確，pipeline 缺一階段。

**處理決議**：此為**平行的資料工程項目，不納入本引擎的評估範圍**。理由是若在評估期間補入校園座標，將無法分辨路線品質改善來自引擎更換或資料補齊。詳見 §15。

### 3.6 效能基準線

與 `WALK_MODE_QUALITY_FIX.md` 記載的 5–33 ms 一致。**本引擎的延遲目標即為此基準線**（§11.1 軸三）。

### 3.6b DEM 的能力邊界（v0.3.0 修正）

**可取得的最高解析度是 20 公尺網格。**

| 來源                                | 取得性                                                   | 判定                  |
| ----------------------------------- | -------------------------------------------------------- | --------------------- |
| 內政部 **20 m 網格 DTM**            | 政府資料開放授權條款第 1 版、免費                        | ✅ 可用，唯一選項     |
| 內政部 **≤5 m 網格 DTM／1 m LiDAR** | **屬「一般公務機密」，限政府機關內部使用、禁止對外提供** | ❌ 取不到             |
| Copernicus **GLO-30**／SRTM         | 全球免費                                                 | ❌ **不得使用**——見下 |

**為何不得使用 Copernicus GLO-30 與 SRTM**：兩者皆為 **DSM（數值表面模型）**，高程含建物與植被。台北密集市區的建物邊緣會被解讀成數十公尺落差，產生大量假坡度。誤用會得到一份「有數字但全是雜訊」的坡度層，且不會有任何錯誤徵象。

**20 m 網格的能力邊界**：取樣間距 20 m 表示可解析的最短地形特徵約在 40 m 以上。而輪椅實際受阻的坡度特徵是：

| 特徵                                 | 尺度    | 20 m DTM 能否反映 |
| ------------------------------------ | ------- | ----------------- |
| 緣石斜坡                             | 1–3 m   | ❌                |
| 人行道短坡、店家出入口高差           | < 10 m  | ❌                |
| 天橋／地下道引道                     | 10–40 m | ❌ 至勉強         |
| 街廓地形梯度（北投、文山、南港山區） | ≥ 100 m | ✅                |

**實測佐證（Phase 0-6，2026-08-19）**：北投＋文山 20 條道路絕對坡度中位 **2.843%**、最大 19.778%、12 條超過 2%；信義計畫區 20 條中位 **0.074%**、最大 **0.448%**、無一超過 2%。**平地未產生假陡坡**，雜訊低於預期。據此補上更精確的界線：**小於約 1% 的結果應視為平地基線，不具無障礙判定意義，不得用於排序**。

**因此本規格對 DEM 的正確定位是**：它提供**街廓尺度的地形梯度**，在台北盆地平地區的鑑別力接近零，在丘陵區有實質價值。它**不是**「補償 OSM `incline` 覆蓋率不足」的等價替代品——兩者測的不是同一件事。

**必要的座標轉換**：20 m DTM 是 TWD97/TM2（EPSG:3826）平面座標的點檔。`src/scripts/inject-osm-dem-slopes.py:45` 以 `self.dataset.index(lon, lat)` 取像素，**假設 raster 的 CRS 與傳入座標一致**。直接餵 TWD97 raster 會**靜默取到完全錯誤的像素而不報錯**。使用前必須 reproject 為 EPSG:4326 並 rasterize 成 GeoTIFF。

### 3.8 有資料 ≠ 有鑑別力（v0.4.0 新增）

取得政府資料後，對 18,304 筆做了分布分析。**結果顯示其中兩項雖然填答率 100%，但作為硬限制或二元判斷幾乎沒有鑑別力**——這是規格設計必須據以修正的事實，不是註腳。

**寬度分布**

| 門檻    |   `SW_WTH` 人行道寬 |  `SWW_WTH` **淨寬** |
| ------- | ------------------: | ------------------: |
| < 0.9 m | **0.60%**（109 筆） | **0.60%**（109 筆） |
| < 1.2 m |               8.77% |          **23.12%** |
| < 1.5 m |              39.41% |          **58.56%** |
| < 2.0 m |              53.74% |          **75.72%** |
| 中位    |              1.80 m |          **1.35 m** |

**推論**：

1. §7.3 原訂的 wheelchair 硬限制「有效寬度 < 0.9 m → INF」**只會命中 0.60%**。它作為安全底線可以保留，但**不能指望它產生選路差異**。
2. 真正的鑑別力在 **1.2–2.0 m 的分級成本帶**——淨寬 58.56% 落在 1.5 m 以下，對輪椅（車體約 0.7 m、迴轉與會車需要更多）正是「勉強可通行」的區間。§7.3 據此改為以淨寬為主的分級懲罰。
3. `SW_WTH` 與 `SWW_WTH` 的中位差僅 0.15 m，但最大值 35.74 m vs 15.10 m——**寬路段的差距才大**。應以 `SWW_WTH` 為 `effective_width_m` 的直接來源，不要用 `SW_WTH` 推導。

**緣石斜坡分布**：18,304 筆中 **17,645 筆（96.4%）** `SW_RAMP > 0`，總計 38,698 座。**「這段有沒有斜坡道」幾乎恆真，作為二元特徵沒有鑑別力。** 若要使用，只能用密度（每段長度的斜坡數）或與 `SW_DIRECT` 交叉，且須先驗證該衍生量真的與通行性相關——本規格不預設它有用。

> **這一節的方法論意義**：本專案已兩次遇到「資料存在但近乎均勻分布」（kerb 斜坡 96.4%、寬度硬門檻 0.60%）。**取得資料之後、寫進成本模型之前，必須先看分布**；填答率高不等於能區分路線。此檢查應納入任何新資料來源的納入流程。

## 4. 系統目標與非目標

### 4.1 主從關係

**主：產品缺陷作為裁判。從：研究深化作為手段。**

驗收以 §2.2 所列、已實測且未解的缺陷是否消除為準；PostGIS 與自訂成本模型為達成手段，可解釋性與技術深度為順帶產出。此排序確保「評估」有客觀計分板，而非兩個引擎各畫一條線後憑感覺比較。

### 4.2 目標

- **G-1**：`travelMode: "walk"` 的無障礙判斷發生於選路當下，而非選路之後。
- **G-2**：wheelchair / elderly / visual_impaired / normal 四種 profile 各有獨立成本函數，跑在同一張圖上。**此為能力目標**；四者中僅 wheelchair 的優越性納入評估主張，elderly / visual_impaired 因台北圖資缺乏鑑別力而不可實證（§11.6）。
- **G-3**：硬性約束（樓梯、超陡坡）為真正的硬性排除，且無解時的降級行為可觀測、可量化。
- **G-4**：使用者即時回報的 hazard 與 TDX 電梯故障參與選路。
- **G-5**：產出與 OTP 的三軸客觀對照數據，依 §11.2 協定量測、§11.3 預先登記的判定規則裁決。

### 4.3 非目標

- **不移除 OTP2 或 Valhalla。** OTP2 持續負責大眾運輸，並作為步行的一等公民落回路徑。
- **階段一不接管轉乘行程中的步行接駁段。** 該項待本引擎穩定後進入階段二。
- **不重新實作最短路徑演算法之外的路由基礎設施。** A\* 於鄰接表上實作，正確性以 Dijkstra 交叉驗證。
- **不在本階段補齊校園設施座標。**（§3.5）

## 5. 系統架構

### 5.1 執行架構決議

**PostGIS 作為離線圖資倉儲 + Node 進程內記憶體圖執行 A\*。查詢路徑不觸及任何資料庫。**

| 階段                                      | 誰負責          |
| ----------------------------------------- | --------------- |
| 離線建圖、空間 join、屬性來源後設         | PostGIS         |
| 開機載入、常駐圖、空間索引、A\*、動態覆蓋 | Node 進程記憶體 |
| **查詢期間的資料庫往返次數**              | **0**           |

**選擇依據**：

1. 六都 105,308 條 way 拆段後仍屬可完整常駐記憶體的規模（§3.2、§5.8）。
2. 目標為 warm 18–20 ms（§3.6）；跨進程架構須先支出連線、SQL 組裝、結果序列化等與演算法無關的成本。
3. 動態成本覆蓋（hazard／電梯故障）須能在**任何被 A\* 展開到的邊**上生效，包含走出起終點外接矩形的繞路邊。唯有常駐覆蓋能保證此性質（§8.2）。
4. 可解釋性來自**資料模型**（`value / source / confidence / updated_at`）而非 A\* 的執行位置；PostGIS 仍可離線回答「這條邊為何昂貴」。

**pgRouting 對照臂已移除。** v0.1.0 原規劃於 Phase 0 同時實作 `pgr_aStar` 與記憶體 A\* 以實測比較。移除理由有二：

- 決議 3 的「查詢路徑零資料庫往返」在架構上排除 pgRouting，兩者已非同一設計空間中的可比選項。
- Phase 0 已包含建圖 pipeline、拓撲切段、出入口對位等高風險工作（§12），再加一整套 pgRouting 實作會使 go／no-go 決策前的投入大到難以收手。

**代價與補償**：本規格因此無法提供「與現成圖資料庫方案的自量測對照」。研究論述改以既有文獻的 in-memory vs. database-backed routing 效能比較，加上本文 §5.1 的架構理由支撐。此為**刻意的取捨**，並在評估報告中明列為限制。

### 5.8 記憶體預算與圖的表示法

v0.1.0 曾聲稱「backend 未設 memory limit，故不會被 OOM kill」。**該陳述錯誤**：V8 old-space 預設上限、Docker VM 記憶體與主機實體記憶體皆構成硬上限。本節取代該陳述。

**圖的表示法是記憶體決策本身，不是實作細節。**

| 表示法                                                                                                | 每條有向邊的量級       | 六都外推                                       |
| ----------------------------------------------------------------------------------------------------- | ---------------------- | ---------------------------------------------- |
| 純 JS 物件圖（`{from, to, attrs:{...}}`）                                                             | 數百 bytes             | 數百 MB — 不可接受                             |
| **CSR／TypedArray（鄰接以 `Int32Array` 偏移表示，成本與屬性以平行 `Float32Array`／`Uint8Array` 存）** | **43.1 bytes（實測）** | **74.33 MB 常駐 / 148.66 MB 峰值（實測外推）** |

**因此本規格要求圖以 CSR（compressed sparse row）＋ TypedArray 表示，不得使用物件圖。** 屬性以平行陣列存放，字串類屬性（`surface`、`wheelchair` 等）先字典化為小整數。

**v0.5.0 修訂（Phase 0-2 實測回填，2026-08-24）**：本節 v0.4.0 的「十餘 bytes／十餘 MB」是估計值，**已被實測推翻，低估約 5 倍**。原估計假設六都約 100 萬條有向邊、每邊十餘 bytes；實際台北一市即有 441,456 條有向邊，依 §3.2 的 4.1 倍外推六都約 181 萬條，且每條有向邊實測 43.1 bytes（CSR 本體 31 bytes，節點陣列攤提 12 bytes）。

**台北實測（`graph-loader.integration.test.ts`，2026-08-24）**：

| 指標                      | 實測值                                |
| ------------------------- | ------------------------------------- |
| 節點數                    | 161,368                               |
| 有向邊數                  | 441,456                               |
| 無向段數                  | 220,728（含 165 個 self-loop 閉環段） |
| TypedArray 精確 footprint | **18.13 MB**                          |
| 每條有向邊                | **43.1 bytes**                        |
| 六都常駐（×4.1）          | 74.33 MB                              |
| 六都熱重載峰值（×2）      | **148.66 MB**                         |

**量測方法（v0.5.0 修正，這是本節最重要的更正）**：

**不得以 `process.memoryUsage().heapUsed` 量測本圖。** TypedArray 的 backing store 是 off-heap `ArrayBuffer`，不計入 V8 heap。實測台北圖在強制 GC 後 `heapUsed` 差值僅 **0.83 MB**，而真實 footprint 是 **18.13 MB**——以 `heapUsed` 回報會低估約 20 倍並得出錯誤的 go／no-go 結論。正確量法是加總 `PedGraph` 上所有 TypedArray 的 `byteLength`（精確值），或讀 `process.memoryUsage().arrayBuffers`。

**預算與驗證**：

- Phase 0 必須量測台北市的實際**節點數、有向邊數與 TypedArray footprint**，而非以 OSM way 數推論，也不得以 `heapUsed` 代替。
- 六都預算以台北實測值乘以 §3.2 的 4.1 倍再留 100% margin 推估，並須在 Phase 4 實際載入時複驗。
- 熱重載期間新舊圖並存，峰值為穩態的兩倍，預算須以峰值計。
- **`--max-old-space-size` 對本圖無效**：該旗標只約束 V8 old-space，管不到 off-heap `ArrayBuffer`。真正的上限是 `docker-compose.yml` 對 backend 設定的 container memory limit，該限制才是必須設定的那一項。

**go／no-go 條件**：若台北實測外推後的六都峰值超出既定預算，須先縮小圖資範圍（回到台北市），不得帶著未驗證的記憶體假設進入 Phase 4。

**Phase 0-2 判定：通過。** 148.66 MB 峰值對 Node 後端可接受。但須明確記錄：通過的理由是「148.66 MB 這個絕對值可接受」，**不是**「符合原訂的十餘 MB 目標」——原目標已被實測推翻並於本版更正。

| --------------------- | -------------------------------------------------------------- |
| `graph_version_id`    | 靜態圖版本（來源檔雜湊 + 建圖時間）                            |

### 6.5 寬度欄位不得互為 fallback（v0.5.0 新增）

`width_m` 與 `effective_width_m` 是**兩種不同的量**，不得以 `COALESCE` 互相逢追：

| 欄位                | 語意                                                                  | 來源                        |
| ------------------- | --------------------------------------------------------------------- | --------------------------- |
| `width_m`           | 人行道**總寬**，或任何納入 highway 的 OSM `width` tag（**含車道寬**） | 政府 `SW_WTH`／ OSM `width` |
| `effective_width_m` | 行人可用**淨寬**                                                      | 政府 `SWW_WTH`              |

實例：同一筆政府資料的總寬 4.01 m 對淨寬 1.65 m。§7.3 的成本帶定義在**淨寬**上，因此 CSR 的 `edgeWidthM` **只取 `effective_width_m`**，缺值即 `NaN`。

**理由是安全方向**：把總寬或車道寬當成行人淨寬會**高估可通行性**，對輮椅路徑規劃是錯的那一邊——這等於把未知當成**已知良好**，是 §7.4「未知不等於最差」的反面誤用。代價是損失約 0.4 個百分點的 OSM-only 寬度訊號（36.32% → 35.90%），這是刻意接受的交換。

### 6.6 self-loop 段與無向邊數的正確收斂（v0.5.0 新增）

台北圖實測含 **330 條 self-loop 有向邊 = 165 個實體閉環段**（`from_node = to_node`，即閉合 way 且中間無路口）。

因此無向邊數**不得以 `from_node <= to_node` 收斂**，那會把每個 self-loop 算兩次：

| 計法                             | 台北實測            |
| -------------------------------- | ------------------- |
| `from_node < to_node`（嚴格）    | 220,563             |
| `from_node <= to_node`（錯誤）   | 220,893             |
| 嚴格 `<` ＋ self-loop 有向數 / 2 | **220,728**（正確） |

正確做法：雙向邊以嚴格 `<` 計一次，self-loop 另計後除以 2，單向邊每條計一次；並断言 self-loop 有向數必為偶數。此差異是整合測試對真圖跑出來才拓到的，純 fake-fixture 單元測試看不到。

陣列設計的連帶約束：`slope_longitudinal` 是**有向**的（反向邊為負值），所以 CSR 的屬性平行陣列長度必須是 **有向邊數**，不得為了節省記憶體讓兩條有向邊共用一列屬性。

## 7. Accessibility Cost Model

### 7.1 與 `scoring.ts` 的職責切割

**嚴格分工，各面向有唯一擁有者。**

| 面向                                 | 唯一擁有者          | 內容                                                                                                                    |
| ------------------------------------ | ------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| **物理通行性**（能否通行、通行難度） | **edge cost model** | slope、cross slope、width、surface、smoothness、steps、kerb、barrier、elevator 連通性、**tactile_paving**、**音響號誌** |
| **服務品質**（行程體驗與周邊）       | **`scoring.ts`**    | 無障礙廁所、周邊設施、環境（天氣／空品）、轉乘懲罰                                                                      |
| **共用 primitives**                  | 抽出供雙方引用      | `MODE_PROFILES`、`slopeContribution` / `widthContribution` / `crossSlopeContribution`、`walkSpeedMps`                   |

> **v0.1.0 矛盾修正**：v0.1.0 將 `tactile_paving` 列為 `scoring.ts` 的服務品質，卻又要求 visual_impaired profile 依觸覺鋪面降低 edge cost，構成雙重擁有者。本版裁定：**觸覺鋪面與音響號誌是 visual profile 的通行性資訊（影響「這條路走不走得了」），歸 edge cost 唯一擁有**，`scoring.ts` 不得再計算。

**強制紀律**：重疊欄位不得雙方各自計算。切割完成後 `scoring.ts` 必須**刪除**自身的通行性計算，改向引擎索取聚合結果。保留備用即構成雙重真相。

**附帶效益**：`A11Y_SCORING_REWORK.md` 記載的根因為「先評分排序、後 enrich a11y、分數從不重算」。當通行性移入引擎、成為選路的一部分，該順序問題在定義上消失。

**附帶效益二**：`scoring.ts:146/162/176` 的 `slopeContribution` / `widthContribution` / `crossSlopeContribution` 目前因 `incline` / `width` tag 近乎為 0 而屬死碼。DEM 合成坡度將使 `slopeContribution` 恢復作用，此為引擎更換帶來的可量測鑑別力提升。

### 7.2 硬限制與軟偏好

資料稀疏性（§3.1）要求已知事實必須絕對執行，不得被距離項稀釋。

```
cost(edge, profile):
    if profile.forbids(edge):        return INF        ← 硬限制
    return length_m
         × slope_penalty(edge, profile)
         × surface_penalty(edge, profile)
         + crossing_penalty(edge, profile)
         + hazard_overlay(edge)                        ← 動態，見 §8.2
```

室內邊無 `length_m`，改以 `traversal_time_s × profile.walk_speed_factor` 為基底。

### 7.3b 硬限制的放寬階梯

第二趟 A\*（§8.3）需要明確的放寬次序，否則實作者無從判斷該放寬哪一項，且引擎可能為避開較輕微問題而穿越更嚴重障礙。

> **v0.5.0 重寫（Phase 0-2 實測回填，2026-08-24）**：v0.4.0 的排序建立在一個**已被 WP-7 推翻的前提**上。原理由寫「寬度覆蓋率僅 0.42%，最可能是未知而非真窄」，引的是 **OSM-only** 數字；但依 §6.3，寬度現在主要來自**政府人行道實測資料**（`SWW_WTH`，匹配段填答率 100%）。已知的寬度不再是「可能是未知」，而是比坡度更可信的測量值——**排序的依據本身失效，因此本版重寫階梯而非只調次序。**

**原則（v0.5.0 明確化為兩個軸）**：放寬次序由「**資料誤判的可能性**」×「**若屬實時的物理後果**」共同決定：最可能是測量誤差、且就算屬實仍物理可通行者先放；最可信且物理上絕對不可通行者最後放。累積式（level k 放寬第①至第ⓚ項），停在第一個有解的層級；回應列出所有**實際**違反項。

**台北圖實測的阻擋規模（決定排序的事實基礎）**：relaxationLevel=0 下 INF 邊共 **36,898 / 441,456（8.36%）**：

| 硬限制           | INF 有向邊 | 資料誤判可能性                                                                                 | 若屬實的物理後果                         |
| ---------------- | ---------: | ---------------------------------------------------------------------------------------------- | ---------------------------------------- |
| 坡度 > 12%       | **26,196** | **高**——DEM 合成，§3.6b 明示 20 m 網格只在街廓尺度有效；且以首尾高程差除長度會對長邊平均掉起伏 | 極難但**幾何上可通行**（可協助推行）     |
| 有效寬度 < 0.9 m |    **542** | **低**——政府實測 `SWW_WTH`（§6.3），非 OSM 稀疏 tag                                            | **物理上不可通行**（輪椅車身加手推餘裕） |
| 無 ramp 樓梯     | **15,054** | **極低**——`highway=steps` 是 OSM 最可靠的標記之一                                              | **絕對不可通行**                         |

（各列相加大於 36,898，因一條邊可同時違反多項。）

**兩個軸在此一致指向同一個排序**：坡度既最可能誤判、後果也最輕（難行而非不能行）；樓梯既最可信、後果也最重。

| profile             | 放寬階梯（由先到後）                               | 理由                                                                      |
| ------------------- | -------------------------------------------------- | ------------------------------------------------------------------------- |
| **wheelchair**      | ① 坡度 > 12% → ② 有效寬度 < 0.9 m → ③ 無 ramp 樓梯 | 依上表兩軸；坡度最可能是 DEM 誤差且物理可通行，樓梯最可信且絕對不可通行   |
| **elderly**         | **無 INF 硬限制**                                  | 依 §7.3，樓梯、坡度 > 12%、寬度 < 0.9 m 對 elderly 皆為高／中成本而非 INF |
| **visual_impaired** | 無 INF 硬限制                                      | 全為軟成本，不觸發第二趟                                                  |
| **normal**          | 無 INF 硬限制                                      | 同上                                                                      |

**不列入階梯：坡度 8–12% 帶。** v0.4.0 把它放在第②級，但它在 §7.3 本來就不是 INF 而是「極高成本」——把**成本放寬**混進**硬限制放寬階梯**是類別錯誤，且會製造一個不改變可行集的空層級（實測序列在該級持平即為此故）。若未來要調整該帶的成本，屬 §11 權重校準的範圍。

**階梯位置不影響回報顆粒度。** 把坡度排到第①級不會讓回應失去資訊：`relaxedConstraints` 列的是該路線上**實際違反**的項目，不是該層級名義上允許的項目。若一條路線實際未用到任何被放寬的邊，它在 level 0 就已有解。

**實測佐證此階梯是必需而非優化**：relaxationLevel=0 時台北圖的最大連通元件由 97.27% 降到 **80.62%**、均勻隨機 OD 連通機率由 94.6% 降到 **65.0%**；全放寬後回到 97.25%／94.6%。即**碎化完全來自成本模型的硬限制，不是圖本身的缺陷**；約三分之一的隨機 OD 在嚴格模式下無可行路線。

**新階梯的逐級解鎖實測（台北圖，2026-08-25）**：

| relaxationLevel | 累積放寬           |          INF 邊 | 最大元件 | P(均勻隨機 OD 連通) |
| --------------: | ------------------ | --------------: | -------: | ------------------: |
|               0 | （全硬）           | 36,898（8.36%） |   80.62% |               65.0% |
|               1 | 坡度 > 12%         | 15,604（3.53%） |   92.57% |           **85.7%** |
|               2 | ＋有效寬度 < 0.9 m | 15,192（3.44%） |   92.62% |               85.8% |
|               3 | ＋無 ramp 樓梯     |    166（0.04%） |   97.25% |               94.6% |

**重點不是「第①級解鎖得比較多」，而是「最小放寬不再連帶物理不可通行的項目」。** v0.4.0 的階梯把坡度排在第③級，而階梯是累積的——一個只需要「放寬坡度門檻」就能成行的 OD，在舊階梯下必須升到第③級，而第③級**同時已經放寬了有效寬度 < 0.9 m**（物理上不可通行）。新階梯的第①級只放寬坡度，寬度硬限制維持到第②級。另外舊階梯的第②級是空層級，會讓 §8.3 的兩趟制白跑一次 A\*。

**回應契約**：`relaxedConstraints` 為陣列，列出**所有**實際放寬項（可能多於一項），並附各項的具體違反量（如樓梯段數與階數、最大坡度百分比、最窄有效寬度）。不得只回報單一項。

### 7.4 未知值的處理

沿用 `A11Y_SCORING_REWORK` 已定案的原則：**未知不等於最差**。未知屬性以中性基準計價，並透過 `confidence` 欄位分離「已知良好」與「未知」，避免在稀疏資料下把所有路徑推向同一成本。

## 8. 查詢執行流程

### 8.1 主流程

```
POST /a11y/accessible-route {travelMode:"walk", mode:"wheelchair", avoidStairs:true}
  │
  ├─ 圖是否已就緒？起終點是否落在六都圖資範圍內？
  │     否 ─▶ 落回 OTP walk，回應 engine:"otp-fallback"        （§5.7）
  │     是
  ├─ 起終點吸附（**記憶體空間索引**，非資料庫查詢）
  │
  ├─ 取用常駐動態覆蓋（**記憶體，非查詢時載入**）           （§8.2）
  │
  ├─ 第一趟 A*：硬限制 = INF
  │     有解 ─▶ 回傳路線，engine:"pedestrian-a11y"
  │
  └─ 無解 ─▶ 依 §7.3b 放寬階梯逐級重跑                       （§8.3）
              回傳路線 + degraded:true
                        + relaxedConstraints:[...]（全部實際放寬項）
                        + 各項具體違反量
```

**查詢路徑的資料庫往返次數為 0。**

> **v0.1.0 修正**：v0.1.0 聲稱「整趟查詢僅一次資料庫往返」，但其 §8.1 主流程先做 PostGIS 吸附、再做一次動態 bbox 查詢，且 hazard 實存於 MongoDB、電梯狀態來自外部 API——實際往返數大於一且跨越三個資料源。本版將吸附索引與動態覆蓋一併移入記憶體，使該項成立且更強。

### 8.2 常駐動態覆蓋

**設計**：hazard 與電梯故障狀態**常駐記憶體**，以短週期背景刷新（或於寫入時失效重載），不在查詢時載入。

**v0.1.0 的 bbox 設計已廢除。** 原設計於查詢開始時以起終點外接矩形撈取範圍內的動態事件。該設計有一個無法修補的缺陷：

> A\* 可能選擇走出起終點外接矩形的繞路（短程 OD 尤其明顯，其 bbox 極小）。那些邊不會被 bbox 涵蓋，因而**未套用動態成本**——引擎會靜默穿越已回報的障礙或故障電梯，使 §4.2 的 G-4 實際不成立，且無任何錯誤徵象。

**常駐覆蓋為何可行**：作用中的 hazard 與故障電梯在城市尺度上是**小集合**（`hazardreports` 目前 0 筆；即使成熟營運後同時有效者亦屬數十至數百量級）。全量常駐的記憶體成本可忽略，且徹底消除涵蓋範圍問題。

**刷新語意**：

| 事件                    | 動作                                                  |
| ----------------------- | ----------------------------------------------------- |
| 使用者新增／確認 hazard | 立即失效並重載覆蓋                                    |
| hazard 過期             | 由排程作業移除（見 §8.4 連帶事項）                    |
| TDX 電梯狀態            | 固定週期背景刷新                                      |
| 評估執行期間            | **凍結**，並記錄 `dynamic_snapshot_id`（§6.4、§11.2） |

### 8.2b 動態事件與邊的綁定

v0.1.0 直接假定可產生 `edge_id → penalty`，但未定義如何取得該對應。實際上兩類來源的識別方式都不是邊：

| 來源            | 原始識別         | 綁定方式                                       |
| --------------- | ---------------- | ---------------------------------------------- |
| `hazardreports` | 座標點（WGS84）  | **載入時**以記憶體空間索引吸附至容差內最近的邊 |
| TDX 電梯故障    | 車站／設施識別碼 | 對應至該站的 `pathway_mode=5` 室內邊（§9）     |

**三項必須定義的規則**：

1. **吸附容差**：超出容差者不綁定任何邊，並記錄為「未能定位的回報」而非靜默丟棄。
2. **方向與側別**：一筆點狀回報預設綁定**該邊的雙向**。道路兩側各有獨立人行道 way 時（台北僅 4,424 條 `footway=sidewalk`，多數路段無此細分），僅綁定吸附到的那一條，不外溢至對側。
3. **跨圖版本穩定性**：綁定關係**不得以外鍵存入資料庫**。`edge_id` 會在每次重建圖時改變；綁定必須於**每次圖載入時重新計算**。此設計使圖重建不會讓既有 hazard 錯位或失效。

### 8.3 兩趟制與失敗政策統一

本設計取代 §2.2 D-4 描述的兩種矛盾政策，統一為單一政策：**第一趟嚴格；無解則依 §7.3b 的放寬階梯逐級重跑，回傳降級路線加明確標記。**

- `service.ts:1609` 現行的 `NO_ACCESSIBLE_ROUTE` 404 分支改為回傳降級路線。
- 放寬為**逐級**而非一次全放：一次只放寬階梯上的下一項，停在第一個有解的層級。若放寬至最後一級仍無解，才回 `NO_ROUTE`。
- 每一趟都必須獨立可觀測：需有自身的 log 與回應欄位（`relaxedConstraints` 列出全部實際放寬項及各項違反量），避免製造新的靜默降級。
- 相較現況僅能回報 `STAIRS_CONSTRAINT_UNSATISFIED`，本引擎知悉每一級放寬所踏的邊，故可回報具體違反內容。此為擁有引擎方能取得的資訊，亦為評估報告的定性佐證。

### 8.4 圖的生命週期

**靜態基底圖（重載）+ 常駐動態覆蓋（刷新）。**

| 資料                       | 變動頻率 | 更新方式                                               |
| -------------------------- | -------- | ------------------------------------------------------ |
| DEM 高程                   | 幾乎不變 | 靜態檔，隨建圖                                         |
| OSM 行人圖 / GTFS pathways | 月       | 重跑建圖 pipeline → 背景熱重載（建好新圖後原子換指標） |
| `osm-a11y` POI             | 月       | 同上                                                   |
| TDX 電梯狀態               | 分鐘     | 常駐覆蓋週期刷新（§8.2）                               |
| hazard 使用者回報          | 秒       | 常駐覆蓋寫入時失效（§8.2）                             |

**關於可重現性（v0.1.0 邏輯漏洞修正）**：v0.1.0 以「即時 patch 會使同一 OD 在不同時刻回不同結果」為由拒絕即時 patch，但**per-request 動態覆蓋具有完全相同的性質**，該理由不成立。

本版的正確立場是：

- 動態覆蓋**本來就會**改變選路結果，這是 G-4 的目的，不是缺陷。
- 可重現性由**記錄**而非由**避免變動**取得：每次評估執行同時記錄 `graph_version_id` 與 `dynamic_snapshot_id`（§6.4）。
- **評估期間動態狀態必須凍結**，且本引擎與 OTP 的對照必須在同一凍結狀態下執行，否則構成未控制的干擾變因（§11.2）。
- 仍不採用「即時 patch 共享基底圖」，但理由改為：熱路徑上的結構性突變會使熱重載與併發查詢的正確性難以保證，而常駐覆蓋已取得相同的即時性。

**連帶必辦事項**：

1. **`hazard:expire` 必須排程化。** 目前僅為手動腳本（`package.json:17`）。hazard 一旦參與選路，未清除的過期障礙將使路線永久繞路且無人察覺——即另一種靜默失效。
2. **熱重載期間記憶體為穩態的兩倍**（新舊圖並存），須以峰值編列預算（§5.8）。

## 9. 室內圖整合

### 9.1 設計

**整張子圖納入引擎。**

- **縫合點**：654 個 `locationType=2` 出入口（全部具備真實座標，§3.4）。
- **站內計價**：以 `traversalTime` / `stairCount` / `pathwayMode` 為成本基底，不使用距離。
- **啟發函數**：見 §9.1b。

### 9.1b 室內節點的啟發函數（v0.1.0 技術錯誤修正）

**v0.1.0 的 `h = 0` 設計是錯的。** 原文主張「`h=0` 恆不高估，於數十節點的子圖中退化為 Dijkstra 無實質代價」——**可採納性（admissibility）確實成立，但一致性（consistency）不成立**。室內節點屬於同一張戶外／室內合併圖：戶外節點使用直線距離、相鄰室內節點突然變成 0，heuristic 在接縫處違反一致性條件。後果是：

- A\* 搭配 closed set 且不重開節點時，**可能回傳非最短路徑**；
- 若允許重開節點以維持正確性，則沿途每座車站的子圖都可能被大量重複展開，p95 延遲顯著上升。

**本版設計**：

1. **代理座標**：每個無座標的室內節點（5,876 個 `locationType=3`）指派其**所屬車站的出入口質心**作為代理座標。
2. **可採納的啟發函數**：`h(n) = max(0, haversine(proxy(n), goal) − R_station)`，其中 `R_station` 為該站出入口相對質心的最大距離。減去 `R_station` 保證不高估——節點真實位置與質心的偏差以該半徑為界。
3. **安全網**：A\* 允許節點重開（re-open）。代理座標使 heuristic 接近一致，重開次數應極少；重開機制的存在是為了在一致性不完美時仍保證最佳性。
4. **驗證**：§13 要求 A\*（含啟發函數）與 Dijkstra（`h≡0` 全圖）於同圖同 OD 必須得到相同成本。此測試會直接抓出一致性造成的次佳解。

**為何 `R_station` 可算**：654 個出入口全部有真實座標（§3.4），故每站的質心與最大半徑皆可於建圖時算出。台北捷運車站尺度約在 100–300 公尺量級，此項扣減不會使啟發函數退化到失去引導力。

### 9.2 為何不採預算矩陣

將每站壓縮為「出入口↔出入口」最短成本表可維持主圖幾何純淨，但**與即時電梯故障不相容**——預算矩陣在電梯停用時即為錯誤，須依 `(車站, profile, 故障電梯集合)` 做失效與重算，複雜度高於直接走子圖。子圖規模（全台 10,220 條邊、單站數十條）使即時遍歷的成本可忽略。

### 9.3 關鍵風險

OSM 的車站出入口與 GTFS 的 654 個 type-2 節點為兩套獨立標記，不保證一一對應。**對位品質直接決定室內圖是否真被使用**——對不上即等同未整合。此為 Phase 0 的驗收項目之一（§12）。

### 9.4 效益

「使用電梯過馬路」「穿越地下街避開樓梯」成為引擎可自行推導的路線，而非特例邏輯。本系統的 `gtfspathways` 資料形狀（`from / to / mode / traversalTime / stairCount`）本即為標準的無障礙 edge schema，無須另訂格式。

## 11. 評估方法

### 11.1 三軸客觀判準

**方法論前提**：不得以 `scoring.ts` 的綜合分數作為裁判。本引擎的成本函數依循同一套無障礙觀點設計，等同直接最佳化該評分函數；以自身目標函數評判自身，勝出為數學必然而非實證結果。判準必須為**引擎無關的客觀事實**。

| 軸                     | 指標                                                                                                              | 現況基準                                               |
| ---------------------- | ----------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------ |
| **一、硬性約束違反率** | 要求某項硬限制時，路線幾何實際違反該限制的比例（樓梯以穿越 `highway=steps` way 判定；坡度／寬度以路線邊屬性判定） | OTP 樓梯 8 組中 6 組違反且靜默                         |
| **二、繞路代價**       | 達成軸一所付出的距離增幅（相對於同 OD 的無約束最短步行距離）                                                      | Valhalla `type=wheelchair` 樓梯 6/6 避開但繞路 8–10 倍 |
| **三、規劃延遲**       | p50 / p95                                                                                                         | 見 §11.2 量測平面                                      |

軸二的存在是為防止軸一被極端繞路達成。兩軸共同呈現「以繞路換無障礙」的取捨曲線，即 profile 權重校準的實證基礎。

### 11.2 評估協定

v0.1.0 未定義量測方式，其延遲基準亦不可用於宣稱非劣性。本節補上。

**協定一：量測平面必須對齊。**
§3.6 的 18／20 ms 是**直接呼叫 OTP 容器 GraphQL** 的數字，不含 Node、吸附、序列化。本引擎的端到端延遲不可與之相比。評估須在**兩個平面各自成對量測**：

| 平面     | 本引擎                            | OTP                             |
| -------- | --------------------------------- | ------------------------------- |
| 引擎核心 | A\* 執行時間（含吸附與覆蓋查表）  | OTP GraphQL 直打                |
| 端到端   | `POST /accessible-route` 完整回應 | 同一端點，強制走 `otp-fallback` |

結論只能在同一平面內下。

**協定二：樣本量。**
每個 OD × 每個平面 **N ≥ 100** 次，捨棄前 10 次暖機。v0.1.0 引用的兩次 warm 值不足以構成 p95。

**協定三：動態狀態凍結。**
評估期間動態覆蓋凍結，本引擎與 OTP 在**同一 `dynamic_snapshot_id`** 下執行（§6.4、§8.4）。否則兩者可能在不同障礙狀態下比較，構成未控制的干擾變因。

**協定四：圖版本記錄。**
每次評估執行記錄 `graph_version_id` 與 `dynamic_snapshot_id`，報告中必須引用。

### 11.3 預先登記的判定規則

v0.1.0 列了三軸卻未定義如何由三軸導出「優於」，使同一組結果可被解讀為成功或失敗。本節在**執行評估之前**固定判定規則，事後不得修改。

**主判定（wheelchair profile，字典序）**：

| 順序          | 條件                                                       | 判定                                                  |
| ------------- | ---------------------------------------------------------- | ----------------------------------------------------- |
| 1（否決條件） | **靜默違反率** —— 違反硬限制且**未標記** `degraded` 的比例 | 本引擎必須為 **0**。非 0 即整體判定失敗，不論其他兩軸 |
| 2（主要條件） | **標記後違反率** —— 違反且已標記的比例                     | 本引擎須**嚴格低於** OTP 同組 OD 的違反率             |
| 3（閘門）     | **繞路代價** —— 相對無約束最短距離的中位數增幅             | 須 ≤ 1.5×。超過即判定為「以不可接受的繞路換取合規」   |
| 4（閘門）     | **延遲** —— 同平面 p95                                     | 須 ≤ OTP 同平面 p95 的 1.5×                           |

**平手與部分勝出的處理**：條件 2 相同而條件 3、4 本引擎較佳者，判定為「不劣且更有效率」，不得宣稱「優於」。任一閘門未過即為失敗，不得以其他軸的優勢抵銷。

**這些門檻是本規格的一部分，須在 Phase 0 結束前確認可量測，並在首次評估執行前凍結。**

### 11.4 臉面效度驗證

3–5 位受試者、10 條路線的小樣本人工評比，用以確認機器判準與人的實際感受方向一致。不做大型使用者研究。

### 11.5 評估資料集

v0.1.0 僅沿用既有樓梯 fixture，該資料集**只能支撐樓梯這一項**的結論。本版要求資料集依判定條件擴充：

| 子集                      | 用途                    | 來源                                         |
| ------------------------- | ----------------------- | -------------------------------------------- |
| 樓梯 OD（既有 14 組）     | 軸一的樓梯項            | `~/otp-backup/walk-quality-fixtures/`        |
| 引擎對照 OD（既有 8 組）  | 軸二、軸三              | 同上                                         |
| **坡度 OD（新增）**       | 軸一的坡度項            | 由 DEM 挑出 >8% 與 >12% 路段的穿越 OD        |
| **過街／號誌 OD（新增）** | visual profile 的成本項 | 由 6,583 個號誌路口與 6,703 條 crossing 挑出 |
| **室內 OD（新增）**       | §9 室內圖是否真被使用   | 由 654 個出入口與 714 座電梯挑出             |

**寬度 OD 子集（v0.4.0 恢復建立）**：Phase 0-6 已確認政府人行道資料可用（§3.7），`SWW_WTH` 填答率 100%。子集取自淨寬 < 1.2 m 的路段（23.12%，4,232 筆）與 > 2.0 m 的路段對照，驗證引擎是否偏好較寬路徑。

⚠️ **但不得以「有效寬度 < 0.9 m」作為軸一的違反指標**——該門檻只命中 0.60%（§3.8），樣本過小且無鑑別力。寬度應以軸二（繞路代價）與分級成本的行為驗證，不進軸一。

全部 OD 位於台北市（§5.6）。

### 11.6 結論的範圍與有效性

**主結論範圍限縮為 wheelchair profile。** v0.1.0 的 §4.2 G-2 宣稱四個 profile，但：

- **`width` 一項限縮已解除**（v0.4.0）：政府人行道資料填答率 100%（§3.7），elderly 的寬度敏感度可被實證。
- **`tactile_paving`（157 個）與 `smoothness`（0.45%）限縮不變**——無任何對應的替代來源，visual_impaired 的核心輸入仍然缺席。
- 缺乏資料即缺乏鑑別力，這兩個 profile 的「優越性」在現有圖資下**不可能被實證**。

因此：

| 主張                                                   | 可否由本評估支持                                                                        |
| ------------------------------------------------------ | --------------------------------------------------------------------------------------- |
| wheelchair 的硬性約束合規優於 OTP                      | **可以**（若通過 §11.3 判定）                                                           |
| **per-profile cost function 在架構上可行**（能力展示） | **可以**——這是架構事實，不需資料密度支撐                                                |
| **elderly** 的路線品質優於 OTP                         | **部分可以**——寬度項有資料（§3.7），但仍缺 `smoothness`；結論須限定在「寬度與坡度維度」 |
| **visual_impaired** 的路線品質優於 OTP                 | **不可以**——`tactile_paving` 全市 157 個、無替代來源，核心輸入缺席                      |

### Phase 1 — 基礎引擎（wheelchair profile）

A\* + 硬限制 → 兩趟制與放寬階梯（§7.3b） → `engine` 欄位與落回機制 → 回應契約（`relaxedConstraints` 與違反量）。

### Phase 2 — 資料層完整化

DEM 坡度貼合 → `osm-a11y` 空間 join → 室內子圖與 654 出入口縫合、代理座標與 `R_station` 計算（§9.1b） → `source / confidence / updated_at` 後設資料。

### Phase 3 — 動態層

常駐動態覆蓋（§8.2） → 動態事件與邊的綁定規則（§8.2b） → `hazard:expire` 排程化 → 熱重載與原子換指標。

### Phase 4 — `scoring.ts` 職責切割（**獨立階段**）

v0.1.0 把此項塞在 Phase 4 與評估同階段，但 §15 明載其影響範圍未估且會動到既有測試。本版獨立成階段並**排在評估之前**，避免評估期間同時進行既有排序契約的重構。

通行性計算移出 → `MODE_PROFILES` 與三條曲線抽為共用 primitives → 既有測試調整 → 回歸驗證。

### Phase 5 — 多 profile

elderly / visual_impaired / normal 三個 profile。定位為**能力展示**，其優越性不在評估主張範圍內（§11.6）。

### Phase 6 — 範圍擴展與評估

六都圖資匯入（含 §5.8 記憶體複驗） → 評估資料集擴充（§11.5） → 依 §11.2 協定與 §11.3 判定規則執行評估 → profile 權重校準 → 評估報告。

### Phase 7（階段二，本規格不含）

接管轉乘行程中的步行接駁段。

## 13. 測試策略

| 層級                 | 內容                                                                                                                                        |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| **演算法最佳性**     | A\*（含代理座標啟發函數，§9.1b）與 Dijkstra（`h≡0` 全圖）於同圖同 OD 必須得到**相同成本**。此測試直接抓出室內外接縫的一致性問題造成的次佳解 |
| **啟發函數可採納性** | 對含室內節點的 OD，`h(n)` 不得大於該節點到終點的實際最小成本；以 Dijkstra 反算實際成本比對                                                  |
| **成本函數單元測試** | 各 profile 的門檻邊界（坡度 8% / 12%、有效寬度 0.9 m、有無 ramp 的 steps）純函數測試                                                        |
| **放寬階梯**         | 依 §7.3b 的次序逐級放寬；須驗證「一次只放寬一項」「停在第一個有解層級」「`relaxedConstraints` 列出全部實際放寬項」                          |
| **兩趟制不得靜默**   | 第一趟無解必觸發第二趟，且回應必帶 `degraded` 與 `relaxedConstraints`                                                                       |
| **落回機制**         | 圖未就緒、範圍外、引擎異常三種情境皆須回 `engine:"otp-fallback"` 且不得靜默                                                                 |
| **動態覆蓋涵蓋性**   | 構造一組「最佳路線走出起終點外接矩形」的 OD，驗證繞路邊上的 hazard 仍生效（此即 v0.1.0 bbox 設計的失效案例，須成為回歸測試）                |
| **綁定跨圖版本穩定** | 重建圖後，既有 hazard 須仍綁定至等價的邊，不得錯位或失效（§8.2b）                                                                           |
| **室內圖**           | 「使用電梯跨越樓層」與「穿越站內避開樓梯」須能被規劃出來                                                                                    |
| **記憶體**           | 載入後常駐 heap 須在 §5.8 預算內；熱重載峰值須以雙圖並存量測                                                                                |
| **路由整合測試**     | 沿用 `tests/helpers/test-helpers.ts` 的 supertest harness，`vi.mock` 引擎層                                                                 |
| **回歸基準**         | §11.5 的 OD 集納入可重跑的評估腳本，記錄 `graph_version_id` 與 `dynamic_snapshot_id`                                                        |

**驗收原則**：綠燈測試不等於功能正確。依既有教訓，最終驗收須將新版本跑在備用埠、與現行版本以同一組 OD 並排對打。
